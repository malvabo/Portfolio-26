Conduit

From a fixed compliance engine to pipelines importers build themselves

Shipped an MVP with the compliance rules baked in on our side, then let testing reframe the product.

Role

Product and design lead

Scope

Operation mapping, product direction, design

Shape

MVP, then a pivot after testing

Domain

Supply chain

Impact summary

  • •Moved the product from our compliance engine to their document infrastructure
  • •Made the pipeline the unit: built once, saved, reused, callable over an API
  • •Split the work into two independent flows instead of one assumed chain
  • •Cut the validation layer to keep the second version shippable

The problem & context

The project began with the operation, not a feature. My first job was to map the real document flows, where people got stuck and where errors piled up, so we could prioritise from evidence, not from the most obvious build.

  • 1.Compliance documentation was high‑volume, repetitive and error‑prone
  • 2.It sat on the critical path for clearing shipments
  • 3.Nothing made the work reusable from one shipment to the next

The first bet

We built an MVP that automated compliance documentation with the rules defined on our side. We encoded what “valid” looked like, ran documents against it, and flagged what did not pass. On paper it was the right scope: opinionated and useful out of the box.

What testing revealed

Once the team started working through the live MVP, the scope did not hold. We found far more rules and edge cases than we had accounted for, and it got clearer as we moved toward larger importers. At that scale compliance is not one ruleset. It bends with the country and the product, and every serious importer already has its own interpretation of what a document must contain.

The rules we had built were ours. What customers needed were theirs, and there was no path to hand‑mapping all of it without turning an MVP into an open‑ended rules‑engineering project.

The pipeline

Pipeline builder: a recipe (the fields to pull or fill) and a trigger (when it runs)

Approach

We stopped being the authority on compliance and became the tool importers use to build their own. To accomplish this:

  • 1.Mapped the operation first, and let the gaps decide where the first release went
  • 2.Made the pipeline the unit of the product, defined by a recipe and a trigger
  • 3.Split the work into Extract and Inject, each able to stand alone
  • 4.Drafted schemas from a description, so setup was not a blank slate
  • 5.Made pipelines persist, so they could be duplicated and triggered over an API
  • 6.Removed validation and narrowed the surface around the two flows

Strategic moment: from our rules to their pipelines

The risk

Pre‑scoped compliance logic could not cover a customer base this varied, and customers had to review it anyway.

The controversy

Abandoning the rules engine meant giving up the opinionated positioning the MVP was built on.

What changed after

The product became configurable, set up against each importer’s own rules.

Two flows, deliberately independent

Extract

Point a pipeline at a supplier’s documents and define the schema. Describe what to pull and the pipeline drafts the fields to edit.

Inject

Inject runs the same pipeline backwards. Detect a form’s layout, place the fields, and fill them with the values you bring.

Each has a standalone job. Extract often ends at extraction, with data going into an ERP and no document to produce. Inject often starts without an extraction, because the form already exists and the values arrived some other way. Chaining them is possible, but making it the definition would model a workflow only some importers have.

The change that mattered was reuse. A pipeline is a saved object. Duplicate it for another supplier, adjust it, or connect it over the API so an incoming document triggers it from the importer’s own systems. Setup done once carries over to the next supplier.

The subtractions

We dropped validation. Mapping every rule across every country and product was extremely hard, it was not what customers asked us to own, and the MVP did not need it to be valuable. Rather than let a half‑built rules engine hold the release back, we parked it.

We narrowed the surface. Triggers collapsed to the two that are unambiguous, an API request or on demand, after a watched‑folder option raised the obvious question of which folder. The inbox stayed background context rather than a place to build pipelines. Even a vanity “documents processed” count gave way to a plain “last updated.”

Impact

2 flows

Extract and Inject, each useful on its own

1 unit

The reusable pipeline, duplicable and API‑triggered

−1 layer

Validation scoped out to keep the release shippable

Closing insight

The MVP did its real job by being wrong in a useful way. Hard‑coding compliance was the fastest way to learn that compliance cannot be hard‑coded for this customer base, and the discipline to remove the validation layer is what kept the second version shippable.
